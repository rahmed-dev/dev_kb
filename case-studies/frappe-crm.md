# Frappe CRM — teardown

Open-source CRM built on Frappe. Read at v1.79.1, 2026-07-23. ~15k lines Python, 323 components /
~47k lines frontend.

Framework-specific by design — this file is evidence. The portable lessons drawn from it live in
`backend/`, `frontend/`, and `practices/`.

## Backend

Object-oriented, but only where the framework already is. One class per record type, subclassing the
framework's base document. **No service layer, no repositories, no abstract base classes** — two
non-document classes exist in the entire backend.

Behaviour sits on the record class. The lead type is 545 lines with `create_contact`,
`create_organization`, `convert_to_deal` as methods. Entry points are one-liners delegating to named
steps; 20 methods on the deal class, none over ~25 lines.

Anything that is a verb rather than a state transition is a module-level exposed function, not a
method.

Three habits worth stealing:

- **Generated type stubs.** Every record class carries an auto-generated typed field block
  (`# begin: auto-generated types`), regenerated by tooling. Free editor completion and type checking
  over the record's fields.
- **UI defaults on the record class.** Default list columns and board settings are static methods on
  the class. The server owns the default shape of the screen; the client asks for it.
- **One schema-driven read module.** 837 lines whose endpoints all take the record type as a
  parameter — records, fields, filters, quick filters. The client never names a field, which is why
  user-defined custom fields appear in the UI with no code change.

## Frontend

Not object-oriented at all. 217 of 323 components in the current authoring style, 2 legacy. Seven
state-library stores, twelve composables, three classes in ~47k lines. The framework's own data layer
in 85 files.

Median component 75 lines — but a heavy tail: 1356, 870, 847, 841, 825. All of them are "the screen
every feature gets bolted onto".

**The form engine.** Rendering arbitrary records as editable forms costs 1586 lines: field renderer
617, layout 111, section 41, column 20, transforms and mandatory checks 175, conditional-visibility
expressions 77, schema store 181, dialog shell 302, dialog API 62 — excluding input controls. Justified
here, because editing arbitrary records *is* the product.

## Extensibility — the part worth copying

Third parties extend by creating a record holding a JavaScript class, evaluated at runtime. The
contract gives it header actions, injected rendered content, and dialogs. Helper objects are closed
over as locals rather than attached to any global.

The good part: **the vendor's own built-in behaviours use the same mechanism**, loaded from a
directory by convention and merged into the same pipeline as the stored ones. Two sources, one path,
so the seam cannot rot unnoticed.

Its own project notes state the intent plainly: third-party apps extend via records, with no source
modification; multiple scripts per type run in sequence, last write wins.

## Costs, stated plainly

- Evaluating stored code is arbitrary execution in every user's browser. Only tolerable because
  authoring is administrator-restricted.
- 118 frontend tests, **pure utility functions only** — zero component tests, on a 47k-line frontend.
- The 1356-line component is not an outlier, it is a pattern: four files over 800 lines, each the
  dumping ground for one screen.

## Process

Ships an `AGENTS.md` and a documentation split of plan / stable contracts / archive, with an explicit
rule to move a section from plan to archive on completion. Conventional commit prefixes, multiple
logical commits per PR, formatting enforced by pre-commit hooks.
